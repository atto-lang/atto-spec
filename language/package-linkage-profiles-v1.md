# Package linkage profiles v1 (proposed)
 
Linkage is a build property, not a source-language effect. Development/release optimization, static/dynamic/hybrid package linkage, AOT/JIT/interpreter execution and runtime/FFI linkage are independent dimensions. Ordinary development defaults to dynamic only on a target with a verified dynamic package implementation; release defaults to static. Sealed AOT, HDL and hard-real-time profiles default to static. Explicit unsupported requests fail with a diagnostic before publishing any new artifact; never silently switch linkage or execution profile. AOT dynamic loading means verified precompiled modules, not source compilation, runtime reflection or a JIT fallback. The sealed closed-world profile remains static; a separately governed precompiled-module AOT profile may admit dynamic modules.

## Package artifact and identity
- Resolve every import from a pinned package instance and effective namespace or isolated file ID. Distinct versions/instances with the same name must not collide; the resolver owns this identity.
- Record canonical target, compiler, runtime ABI, semantic profile, public/namespace ABI, ownership/lifetime/effect/refinement contracts, generics/embedded body digests, actor protocol/state layout and capability requirements. Include exact artifact digest and transitive lock resolution. Canonical serialization must be unambiguous and versioned.
- Validate authenticated expected metadata and exact immutable bytes BEFORE executing loader constructors or init hooks. Never trust self-asserted manifests, ambient search paths, mutable symlinks or path re-open after verification. Retain verified handles, verify dependency closure and deny unapproved host symbols/capabilities. Signatures/trust roots are deployment policy, not a hash alone.
- Package-static means guest package objects/archives linked into the consumer; system libc and host runtime linkage are separate declared facts. Package-dynamic means separately produced precompiled modules resolved at load time. Hybrid selects explicit package strategies. Shared objects on disk alone do not prove safe Atto dynamic loading.

## Incremental semantics
Cache parse by file, semantic admission by namespace/declaration, target codegen by exact target/profile/semantic dependencies, link by ordered object and dependency artifact identities. Body-only changes with stable ABI recompile only affected units and consumers embedding code. Static consumers relink using cached objects; dynamic consumers need not relink if their verified import ABI and pinned deployment manifest are updated compatibly. Changed ABI/ownership/suspension/actor protocol/negative lookup invalidates affected semantic dependents. Missing dependencies, corruption, failed compile/link or cancellation never publish a partial successful build; retain last successful artifact. Use atomic publication and clean-vs-warm differential tests. Static/dynamic/optimization modes may reuse verified frontend entries but cannot share incompatible codegen or link artifacts.

## Safe generation replacement
Loading and hot replacement are separate capabilities. Stage and validate entire closure before publishing a generation. Retain old code until all executing and suspended frames, tasks, actor/mailbox references, callbacks, closures, FFI handles and deferred cleanup using it have quiesced. Fence late work by generation. Incompatible ownership, effect, capability, ABI or state changes reject before publication unless an explicitly verified migration protocol exists; no automatic state migration claim. Rollback preserves prior generation; no unloading on cancellation alone.

## Required parity gate
For each supported target execute identical .atto sources under dev/release × static/dynamic/hybrid. Verify artifacts actually use requested linkage; compile/run clean, no-op warm, compatible body edit, public ABI change, deletion, alias/lock rebind, corrupt artifact, missing dependency, unsupported mode, generation pinning and failed publication. Check exact compiler commit/tree, fixture blobs, toolchain/target, actual commands and runner steps, output and diagnostics, object reuse, artifact digests and linkage inspection. Host-only canaries and zero-step jobs are never guest proof. Unsupported profiles are explicit and not counted as parity. Native Image host AOT, .NET host AOT, JS module bundling, Wasm module instantiation and HDL elaboration are distinct mechanisms, not interchangeable claims.

Proposed CLI: atto build --dev|--release --link=static|dynamic|hybrid; names remain proposed until integrated with the existing CLI contract. No new guest syntax.
