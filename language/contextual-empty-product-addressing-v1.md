# Contextual empty products and addressing domains — candidate v1

Status: OWNER-DIRECTED MODEL, detailed edge rules are CANDIDATE, compiler/guest NOT_EXECUTED. Companion to #303, #306, #315 and spread correction #321. This proposal does not silently rewrite an already published profile.

## Product abstraction and literal resolution

Tuple and Record share a structural Product abstraction (name and public type/trait/generic spelling provisional). Tuple slots are ordered, heterogeneous, and implicitly identified by contiguous nonnegative integer indices. Closed Record slots have unique static names from the ordinary variable/formal identifier domain, and heterogeneous types. Record structural type identity ignores source field order; construction effects still follow written order. Product does not imply a dictionary, dynamic dispatch, shared heap representation, common equality across kinds, runtime reflection, or new public key APIs.

The empty parenthesis literal is an unresolved zero-arity product until contextual type checking. If a unique compatible expected concrete Tuple or Record shape permits zero slots, resolve to that kind. With no such expectation, default to empty Tuple. A bare Product expectation defaults to Tuple as its concrete subtype (candidate); do not introduce a third concrete empty representation. An already materialized Tuple or Record retains its type: no implicit conversion in bindings, assignments, return, argument passing or spread. A nominal user-defined type named Record, Tuple or Product cannot acquire intrinsic authority by spelling. Generic substitution must resolve builtin identities and actual closed shape before admitting contextual construction. A closed nonempty expected shape rejects an empty literal. Open Record/row shape, exact generic spellings and public Product interface require separate ratification.

Proposed contextual sites: direct initializer, annotated return, unique resolved formal, and recursively propagated expected field/element types of a statically known aggregate, where ordinary type checking supplies that type. A naked literal at an untyped nested site defaults to Tuple. Do not propagate the enclosing aggregate kind to all its children. Do not infer an omitted argument from an empty value. An unconstrained generic must not invent named fields. Overloads simultaneously admitting the empty literal as Tuple and Record are ambiguous; no candidate retries or default-Tuple preference to select a concrete overload. Explicitly typed intermediate binding disambiguates. A default-Tuple fallback in no-context inference is not an overload ranking rule. A common Product formal accepts the concrete default or an explicitly resolved subtype; erased Product is not automatically a statically known spread shape. Candidate specificity ranking for Product vs concrete overloads is deferred to general overload rules.

## Contextual singleton Tuple — owner-directed extension

An ordinary parenthesized single expression without a trailing comma defaults to scalar grouping, not a Tuple. A unique statically known builtin Tuple expectation may instead construct a singleton Tuple when its exact shape permits one element; both `const Tuple t = (42);` and `const Tuple t = (42,);` are valid. The expected element type is applied recursively to the inner expression. The explicit comma always denotes a Tuple, and a nonempty expected shape of incompatible arity or element type rejects. This is literal contextual construction, not conversion of a previously materialized scalar or aggregate. No implicit wrapping of a bare scalar identifier without parentheses; a parenthesized identifier under Tuple expectation supplies that one element with ordinary copy/borrow/move checks. The special rule does not reflect Pair keys into Record fields or reinterpret a named Record literal as a Tuple. Bare Product expectation does not by itself select singleton construction.

Candidate overload ranking: ordinary scalar grouping exact match wins over contextual singleton wrapping, if otherwise equally viable under normal overload rules; unique Tuple-only formal admits wrapping; ambiguous equally ranked Tuple expectations reject. Empty () remains ambiguous between Record and Tuple overloads. Call delimiters are not grouping delimiters: f(42) cannot use this rule, f((42)) can. Resolve the expected shape before emission, evaluate the inner expression once, and preserve cleanup, effects, ownership and identity. Contextual recursion and overload budgets must be bounded. General nested, return, call and overload execution remains unverified; local scalar compiler admission is the initial implementation slice.

## Addressing domains and syntax

For nonempty products, classify each delimiter level from its own tokens. Ordinary parentheses default to scalar grouping or positional Tuple construction (with the contextual singleton rule above) unless explicit identifier-colon or identifier-equals fields select Record. In the latest model (a proposed reconciliation of #303/#306), brace Record entries can reflect a statically identifier-proven inline Pair key into a field; ordinary parentheses do not reflect Pair keys. An all-Pair tuple remains Tuple regardless of surrounding expected Record type. Mixed parenthesized field and inline Pair entries, capture syntax, quoted-colon Map versus Record and untyped empty braces require explicit reconciliation with earlier profiles; keep them as decision probes, not unconditional executable admission. Typed empty Record braces remain supported; typed Map braces do not become Product. Function-call delimiters are not aggregate delimiters: ordinary f(a=5) binds a formal; f({a:5}) passes one Record. Nested grouped Record argument spellings must be reconciled with the earlier hold in #306; record values must never be silently flattened into calls.

Record names must be valid ordinary source identifiers under the canonical lexer, including its reserved-name and Unicode policy. They need not be existing variable bindings. If quoted labels are admitted by the selected profile, validate the entire decoded string using that same policy; no special trimming, casing or normalization. Reject invalid names, duplicates after decoding, and arbitrary/computed keys for closed shape. Pair keys remain arbitrary strings; Map keys use Map rules. Capture and literal label are not the same: capture needs a lexical binding. Tuple indices are not stored keys and may not be confused with a contained Pair's key, including numeric-looking string keys. Tuple index access has no implicit string coercion; Record numeric index is not its field offset. A static index must fit the actual arity. Dynamic heterogeneous index result typing, negative indexing, reflection/enumeration and cross-kind equality are explicit decision probes, not newly admitted features.

## Spread and representation

Tuple call spread passes complete elements by index; Record call spread passes complete field values by static names. Never inspect Pair keys or unwrap Pair payloads as a side effect of either. Only explicit constructors/conversions may do that under their own contracts. Zero-slot spread consumes no parameter and does not reset the named-argument phase; still evaluate the written operand once, including an effectful function returning an empty product, if the ordinary effect system admits it. A plain empty product argument is ONE argument, not omitted, and not zero arguments. No implicit recursive flattening. For a statically resolved empty literal used as spread, zero slots and no ambiguity about binding names; overload selection still follows ordinary callable arity and defaults, not an invented type. An erased Product operand without a proven shape rejects spread. Retain all normal ownership, borrow, effects, failure and cleanup rules. Empty representation may be zero-sized but must not erase static kind, overload identity, or semantic type checks; no new allocation guarantee without backend proof.

## Conflicts and evidence

#303's declaration-only empty exception is generalized in this candidate, but its nonempty expected-type Pair-to-Record override would conflict with the latest no-reflection model. #306 allows mixed parenthesized Pair entries; #315 proposes named Tuple projection. These are explicit review points, not silently promoted. #321 positional/named spread rule remains invariant. Keep existing profiles stable until reconciliation. Require exact production parser/type/ownership/formatter tests, real guest evidence, and semantic rejection without artifact; unsupported-feature diagnostics never count as passing semantic negatives. Bound recursive type/shape resolution using existing resource limits; no host overflow. No backend support, GC-free claim, or private source export is asserted.
