# Readable and Writable capability dispatch v1

Status: proposed extension to the merged [I/O shorthand](io-direction-shorthand-v1.md), [stdio endpoints](stdio-channel-endpoints-v1.md), and [operator spelling](bitwise-and-stream-operators-v1.md). No new guest execution is claimed.

## Capability and dispatch
Readable<T> and Writable<T> are nominal standard capabilities, not unrestricted operator overloading. A user-defined type may explicitly implement them; coincidentally named methods do not confer capability or permission. A duplex type can implement both with different element types. Compiler resolves a unique accessible witness using the static type, checks generic substitution, receiver ownership and effects, then lowers exactly once to the same operation as the named read/write method. Reject ambiguous witnesses rather than select at runtime. Exact declaration grammar is subject to the existing interface/trait grammar; the following signatures are semantic schemas, not a claim that new syntax compiles.

- Readable<T>: susp read() -> Result<Option<T>, IoError> for the baseline fallible stream profile.
- Writable<T>: susp write(value) -> checked WriteOutcome<T> for the baseline atomic item profile. Outcome distinguishes accepted, rejected with original owner, and indeterminate where applicable. A copyable-only profile may use Result<void, IoError> where no affine value can be lost.
- Channel<T> retains its existing readch/writech outcomes, including lossless TryWriteResult<T>; reactive bridges preserve the existing Result<Option<T>, Option<E>> terminal encoding rather than coercing it silently. Adapters with a distinct outcome must use their actual typed witness. No blanket ABI/type migration is implied.
- nb registers once and returns the actual Future<Outcome>; try never registers and distinguishes WouldBlock from EOF or error. Named method spellings for these modes remain API integration choices; no implicit detached task.

## Single operation
sink << value, source >> val result, val result << source, and existing unary/postfix read forms perform one operation. Explicit readch/writech remain channel aliases. Ordinary captures bind the full outcome; selected success arms bind payload only. Existing mutable-slot assignment is not generalized by this amendment. No implicit unwrap, discarded checked error, stream pump or numeric shift. Continuous transfer uses pipe/rpipe. Numeric shifts use <<< and >>>; generic closers remain contextual. Do not reinterpret terminal functional pipeline capture as an I/O operation.

## Readiness, completion, ownership
A potentially suspending operation requires the declared suspension effect even if ready immediately. Readiness check and waiter registration must be one atomic protocol or use register/recheck; readiness notification is not itself commit. No busy polling or scheduler-thread parking. Resume only on the owning task lane, with generation/incarnation validation. Close/cancel/commit races have one winner. Cancellation before admission returns the original affine owner (or leaves it with the caller under an explicit reservation contract); after admission it must not claim a rejected write or transfer a duplicate owner. For external byte writes, report exact committed prefix and retained remainder when known; unknown completion is IndeterminateWrite, never automatically retried. Acceptance, physical flush and durable persistence are distinct. EOF is terminal, not data; drain committed channel items before EOF. Do not suspend with forbidden critical-state or mutable loans.

## Standard I/O and reactive adapters
stdio.in / process.stdin are the same read-only context-owned channel capability; stdio.out / process.stdout and stdio.err / process.stderr are stable separate write-only capabilities. Preserve explicit byte/line framing, permission policy and per-endpoint order. A guest cannot gain read or close authority merely through aliasing or implementing a trait. Stdout admission is not a flush guarantee.
Observable<T> is a producer description, not a global cursor. Each readable Subscription<T> has independent bounded demand and terminal state, unless an explicitly exclusive channel bridge is used. Observer<T> or Subject<T> exposes a writable view only when it defines checked admission/backpressure, ownership and terminal behavior. A subject's readable view is a subscription; a push-only observer with no meaningful acceptance guarantee is not automatically Writable. For reliable broadcast, admission must account for all required recipients before commit or return a checked failure; no silent drops, unbounded buffering, implicit fan-out cloning of affine values or callback execution on an unrelated actor lane. Explicit lossy policies must identify dropped data. Terminal completion/error/cancel is irreversible; physical ACK is separately accounted. No new reactive terminal encoding is introduced here.

## Select
SelectableRead/SelectableWrite are additional capabilities, not inferred from read/write. Register alternatives without speculative consumption/publication; exactly one successful guard commits, losers retain ownership. Closed/EOF/error and all-terminal selection remain observable; nb select cannot hide a suspending arm. A socket readiness API alone is not a selectable commitment witness.

## Backend acceptance
Require real compiled guest positives (directional stdio, generic witness calls including a custom implementation, empty/full and rendezvous, subscriptions, result tags) and negatives (wrong direction, wrong payload, coincidental methods, ambiguous witness, runtime const, illegal suspension/loan, select without witness, numeric shifts and nested generics). Instrument lost-wake/cancel/close/commit and per-subscriber boundedness. Exercise Java/Graal, LLVM, .NET NativeAOT, Wasm, Forge, Rust, JS, Cranelift and HDL according to target profile; unsupported profiles reject without artifacts, not PASS. Host reference tests prove only the model. Exact source head, tree and executed steps are required for guest evidence. Private CI carrier only if authorized; validate every original blob/mode and tree, use no cross-org secret and never bypass branch policy.
